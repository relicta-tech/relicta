# Relicta 5.0.0 — draft release notes

> Draft for review. Relicta's plan currently recommends 5.0.0 from v4.2.0; this version has not
> been approved, tagged, or published.

Relicta 5.0 adds independent package versioning for monorepos, broader version-file support, and
database-backed release and governance history. Teams can version changed packages separately,
keep version files in sync, and review release evidence through the repository's shared governance
plan and approval.

## Highlights

### Release packages independently in a monorepo

Plan versions from each package's own changes. Relicta can write package-specific versions,
changelogs, and tags. Governance planning and approval remain repository-wide, while teams can
release a changed service or library without versioning every package in the repository.

### Update more version files in one release

Relicta can update several version manifests in different supported formats, including Gradle
properties. This helps keep package metadata aligned when a project publishes to more than one
ecosystem.

### Keep release and governance history across runs

SQLite and PostgreSQL can store release runs and governance memory. Teams can import existing
release history, record deployment evidence, and review the audit trail behind release decisions.

### Draft customer-facing release notes with your coding agent

Relicta provides a version recommendation and a structured summary of the changes. Your coding
agent can use that evidence and the product context from your conversation to write customer-facing
notes, then save the draft to the release for review and approval. Relicta keeps the draft attached
to the release so the text reviewers approve is the text that proceeds through publishing.

### Make release policy enforceable

Configured branch and freeze-period rules are now enforced in the release workflow. When a
release exceeds a freeze window's `max_risk`, its evaluation requires approval, or rejects it
when strict mode is enabled. Relicta also fails clearly when required Git credentials or
attestation-signing configuration are missing, instead of continuing with unusable settings.

## Upgrade note

### Go module path for v5

When Relicta 5.0.0 is published, its Go module path will be
`github.com/relicta-tech/relicta/v5`. Go applications that import Relicta packages must change
their imports and `go.mod` dependency from `/v4` to `/v5`. After that release is available, install
the CLI with:

```bash
go install github.com/relicta-tech/relicta/v5/cmd/relicta@v5.0.0
```

The v4 module remains available at its existing `/v4` path.

### Other compatibility changes

The `relicta notes --ai` flag has been removed. Configure AI note generation in `.relicta.yaml`
instead:

```yaml
ai:
  enabled: true
```

Set `ai.enabled: false` or leave it disabled to use deterministic release notes. The setting now
controls AI notes consistently across the notes and release workflows.

Release commands now enforce configured `workflow.allowed_branches` restrictions. A release
attempt from a branch outside that list is refused. Configured `governance.freeze_periods` now
apply each window's `max_risk` threshold. When a release exceeds it, the evaluation requires
approval, or rejects the release when strict mode is enabled. Review these settings if an existing
release process begins stopping at a policy gate.

The machine-readable EU AI Act Article 12 supporting-evidence export now names its timestamps
`releaseProcessStartedAt` and `releaseRecordedAt` (and uses matching CSV column names). Update any
consumer that previously read `startedAt` and `endedAt`; these values describe Relicta release
records and process duration, not the start or end of an AI system use. The report also replaces
`auditChainIntegrityVerified` with `auditChainIntegrityStatus`; this export reports `not_checked`
because chain verification runs through `relicta audit verify`, not during report generation.
